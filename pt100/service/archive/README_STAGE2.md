# Второй этап PT100

> Архивное описание версии от 07.10.2026. Актуальная прошивка, карта Modbus,
> сборка и распиновка описаны в [README.md](../../README.md). Теперь по умолчанию
> три канала, бинарный Modbus через USB COM и запуск только командой START.

Реализован программный сбор четырёх сырых значений MAX31865 на STM32F411CEU6.
Транспорт временный: USB CDC, четыре ASCII-колонки. Modbus, RTC, температурные
формулы, фильтры, калибровка и запись Flash сюда не включены.
Старые `main.c`, `MAX31865.c/.h` сохранены в `Legacy/*.txt` вне компиляции.
Старый драйвер был одноканальным, с включённым PT1000 и фиксированной поправкой.

## Предлагаемое подключение Black Pill F411

Общая SPI1: PA5 → SCLK, PA6 ← SDO, PA7 → SDI. Общая земля.
Логические уровни 3,3 В; питание и переделку конкретного модуля под 4 провода
проверить по его схеме. Программная настройка 4-wire не заменяет переделку платы.
Для PT100 необходим соответствующий опорный резистор на каждом модуле.

| Канал | CS | DRDY |
|---|---|---|
| 1 | PA3 | PA2 |
| 2 | PB0 | PB12 |
| 3 | PB1 | PB13 |
| 4 | PB10 | PB14 |

Первый канал и существующая SPI1 сохранены. USB использует PA11/PA12.
Все CS до настройки MAX поднимаются в 1. Каждый DRDY подключается отдельно:
это push-pull выход, объединять четыре DRDY электрически нельзя.
Распиновка отражена в `pt100.ioc`, `main.c` и `pt100_board.h`.
DRDY опрашиваются в основном цикле без HAL_Delay, SPI из ISR не вызывается.
Неиспользуемый прежний обработчик EXTI2 не включается в NVIC.

## Модули и переносимость

| Модуль | Назначение | Зависимость от STM32 |
|---|---|---|
| `max31865_driver` | Контекст на микросхему, конфигурация с проверкой, сырые данные и ошибки | Нет, callback SPI-транзакции |
| `pt100_acquisition` | Четыре канала, готовность, таймаут, статусы, замеры времени | Нет, callbacks DRDY и счётчика |
| `pt100_ascii` | Форматирование временной строки | Нет |
| `pt100_stream` | Очередь 16 строк, повтор при busy, счётчик потерь | Нет, callback отправки |
| `pt100_stm32` | SPI HAL с конечным таймаутом, GPIO, DWT | STM32F4 HAL/CMSIS |
| `pt100_board` | Пины, таймаут кадра, режим триггера, выдержка bias | Конкретная плата |
| `pt100_app` | Соединение модулей и запуск каналов | Плата и USB CDC |

Перенос на F407: создать CubeMX-проект для точной модели/платы F407; настроить
HSE/PLL, USB 48 МГц, SPI и GPIO; использовать его startup, linker script и CMSIS
заголовок F407. Скопировать перечисленные модули, настроить `pt100_board.h`,
вызвать `pt100_app_init(&hspiX)` после инициализации периферии и
`pt100_app_poll()` в основном цикле. Перенести USER CODE USB-адаптера, включая
копирование TX-буфера, line coding и диагностику. Четыре переносимых модуля
изменять не требуется. Простой заменой define F411 → F407 текущий проект не
портируется: в поставке есть только CMSIS-заголовок F411.

Все вызовы библиотек выполняются последовательно из main, без динамической
памяти. Потокобезопасность для RTOS не заявляется. USB обслуживается прерыванием;
проверка состояния и передача собственного USB-буфера защищены от reset/deinit.

## Измерения и ошибки

По умолчанию `PT100_WAIT_ALL`: дождаться низкого DRDY всех четырёх каналов,
затем последовательно прочитать каналы 1–4. При таймауте 100 мс готовые каналы
читаются, остальные отмечаются как неготовые; приложение продолжает работать.
При отсутствующем канале частота выдачи становится примерно 10 кадров/с.
MAX запускаются последовательно, поэтому этот режим не обещает синхронности
измерений; ожидание готовности также не гарантирует отсутствие пропусков
преобразований при расхождении частот внутренних генераторов MAX.

Для сравнения можно изменить `PT100_TRIGGER_MODE` на `PT100_TRIGGER_FIRST`:
DRDY первого запускает чтение всех четырёх. Если другой канал ещё не готов,
его прочитанное значение сохраняется в структуре, но отмечается NOT_READY
и не выдаётся как достоверное. Отдельные DRDY нужны и для этого эксперимента,
чтобы оценить пригодность первого сигнала как общего триггера.

`pt100_last_frame` хранит raw 0..32767, RTD fault bit, Fault Status и статус
каждого канала: VALID=0, NOT_READY=1, BUS_ERROR=2, SENSOR_FAULT=4, INIT_ERROR=8.
Статусы являются маской. Ошибка SPI не превращается в валидный ноль.
Конфигурация каждого чипа проверяется чтением обратно. Канал с неудачной
инициализацией остаётся отключённым до повторной инициализации/перезапуска.
SPI-таймаут одной транзакции — 2 мс; CS отпускается также при ошибке.

Fault Status читается при каждом получении данных и остаётся защёлкнутым:
автоматический сброс не скрывает неисправность. Для явного подтверждения есть
`max31865_clear_faults()`, без команды управления через COM на этом этапе.
Активный диагностический цикл поиска обрывов проводов здесь не запускается;
чтение Fault Status не означает, что проведены все такие проверки MAX31865.
После аппаратного сбоя повторный запуск/сброс выполняется после устранения причины.

Начальная последовательность: включить bias всех каналов, выдержать 10 мс,
запустить continuous conversion. Выдержку `PT100_BIAS_SETTLE_MS` проверить
для RC конкретных модулей: даташит требует не менее 5τ + 1 мс.
Датчики и номиналы резисторов не влияют на формат raw; пересчёта в градусы нет.

## Формат и запись

Пример: `7621 7625 7622 7624\r\n`. Ровно четыре колонки, разделитель пробел.
Недостоверный канал выводится как `-1`, отличимый от допустимого ADC=0.
Это временное соглашение находится только в `pt100_ascii.c`.
Подробные ошибки и метрики доступны через отладчик, а не в четырёхколоночном файле.

Открыть USB COM в терминале с capture либо установить `pyserial` в Python
и выполнить `python tools/capture.py COM5 capture.txt --seconds 60`.
Без `--seconds` запись идёт до Ctrl+C. Существующий файл не перезаписывается.
Файл содержит только четыре значения на строку. Программа не добавляет время
приёма ПК как будто это момент измерения АЦП. На реальном COM скрипт не проверен.

Буфер USB принадлежит USB-адаптеру до завершения передачи. Принятая им строка
копируется из очереди. При busy/disconnect очередь ждёт, при заполнении
отбрасывается новая строка и увеличивается `pt100_stream.dropped`.
После reconnect могут прийти накопленные старые строки. USB reset может оборвать
уже принятую передачу; доставка без потерь и подтверждение записи ПК не обещаются.
`pt100_stream.accepted` означает принятие USB-адаптером, не запись на диск.

## Временной бюджет

Текущая настройка: PCLK2=48 МГц, делитель SPI=16, SCLK=3 МГц, mode 3.
Одна burst-транзакция: адрес + регистры 0x01..0x07 = 8 байт, 64 такта.
Четыре канала: 256 / 3e6 = **85,33 мкс** чистого времени шины.
Разница начала чтения каналов 1 и 4: минимум **64 мкс** чистой шины.
HAL, GPIO и прерывания добавляют время. Это разница чтения, не моментов АЦП.

Максимальная строка: 4×5 цифр + 3 пробела + CRLF = 25 байт.
Для физического UART 921600, 8N1 это 250 / 921600 = **0,2713 мс**.
Здесь используется USB CDC: значение 921600 согласуется через line coding,
но не устанавливает фактическую скорость USB. Время доставки зависит от USB
и хоста, поэтому UART-расчёт — только сравнение, а не измерение этого устройства.

50 Гц в config MAX — подавление сетевой помехи. Установившийся период при нём
20 мс тип., 21 мс макс.; первая конверсия занимает дольше, до 66 мс.
В теории SPI имеет большой запас относительно 21 мс. Подтверждение на железе:

- `pt100_last_frame.read_ticks`, `pt100_acquisition.max_read_ticks` — время обхода;
- `channel[3].read_offset_ticks - channel[0].read_offset_ticks` — задержка чтения;
- `period_ticks` — период формирования кадров, не гарантированный период АЦП;
- `ready_span_ticks`, `channel[i].ready_offset_ticks` — разброс впервые
  замеченных низких DRDY; точность ограничена задержками основного цикла;
- `pt100_usb_stats.last_transfer_ticks/max_transfer_ticks` — submit → USB complete;
- `submitted/completed/aborted/long_transfers` — состояние передач, stall ≥1 с
  исключается из цикловых временных метрик;
- `timeout_frames`, `bus_errors`, `sensor_errors`, `pt100_stream.dropped` — сбои.

Все ticks — циклы CPU: мкс = ticks × 1e6 / `pt100_tick_hz`.
Разности учитывают один переход через ноль DWT (при 96 МГц полный оборот около
44,74 с); долгие остановки отладчиком делают измерение неоднозначным.
Для точной разницы готовности АЦП подключить логический анализатор ко всем DRDY
и CS; программные наблюдения не заменяют захват фронтов.

Основание для регистров и временных характеристик:
[MAX31865 datasheet, rev.3](https://www.analog.com/media/en/technical-documentation/data-sheets/max31865.pdf),
таблица Electrical Characteristics, разделы Configuration, Fault Status, DRDY.

## Сборка и проверка

Открыть проект `pt100` в STM32CubeIDE, выполнить Refresh и Clean / Build.
Все новые `.c` находятся в существующем source folder `Core`; дополнительные
пути include не нужны. Содержимое исходной папки `Debug` — старые артефакты,
включая makefile с путём `C:\Develop\STM32\pt100`: его напрямую не использовать.
Старый `Debug/pt100.elf` не является результатом этих изменений.

Независимый путь сборки: `./build_stage2.ps1 -ToolchainBin 'путь к GNU Arm/bin'`.
Скрипт компилирует текущие исходники и создаёт ELF/HEX в `build-stage2`.

Проверки на этой машине:

- `tests/run_tests.cmd`: нативные тесты MSVC, /W4 /WX; драйвер, независимость
  четырёх экземпляров, config readback, SPI fault, fault status, DRDY timeout,
  переполнение счётчиков времени, ASCII, очередь busy/overflow.
- `tests/check_arm.ps1`: компиляция 8 новых/изменённых исходников ARMClang
  под Cortex-M4/F411, -Wall -Wextra -Werror. Это проверка объектных файлов,
  не полная линковка GCC-проекта; GNU syscalls/newlib другим компилятором не проверяются.
- Полная линковка ELF/HEX не выполнена: ARM GNU toolchain / CubeIDE не найден.
  F407 и физическое устройство пока не проверены.

Перед приёмкой второго этапа собрать проект GNU/CubeIDE, подключить четыре
модуля по таблице, проверить соответствие колонок каналам и запись TXT,
обрыв/отключение одного датчика, пропажу DRDY, USB disconnect/reconnect,
счётчики потерь и измеренные времена. Затем сравнить WAIT_ALL и TRIGGER_FIRST
по DRDY и решить, допустим ли один триггер для требований эксперимента.
